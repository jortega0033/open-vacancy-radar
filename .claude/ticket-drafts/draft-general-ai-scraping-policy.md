## Goal
Record why "have an AI agent do the scraping, hold results back from the UI, let the source pool grow continuously" is rejected as a *general* architecture for this project -- not a Built In-specific objection, a structural one.

## The claim being evaluated
That routing job discovery through an AI browsing agent, and not surfacing results immediately, makes broad/continuous scraping legally and architecturally fine, even for sources this project hasn't individually reviewed.

## Why it doesn't hold, in general

**Legality is per-source, not per-tool.** Whether automated collection is allowed depends on that specific site's `robots.txt`, Terms of Use, and any API agreement -- exactly the three things checked individually for Built In in `draft-builtin-source-research.md`. An AI agent doing the fetching instead of a hand-written scraper doesn't change what the target site authorized; it's still "an automated device or mechanism" under the kind of clause Built In's terms use, and most job boards/aggregators use similar language. Every source this project has actually adopted (`packages/vacancy-engine/src/global-remote/source-registry.ts`: Himalayas, Jobicy, Remotive, Freehire, Adzuna, Jooble, Reed, JobsPipe; `packages/vacancy-engine/src/ats/*`: Greenhouse, Lever, Workday, JSON-LD, etc.) went through individual review and got a documented reason, state (`active`/`configuration_required`/deferred), and often a gating API key -- there is no "AI agent" exception to that in the existing architecture, and issue #32's decision is explicit: *"every provider must independently satisfy OVR's source policy before any implementation is considered"* -- no wholesale/blanket coverage regardless of what does the fetching.

**Deferred output timing doesn't cure unauthorized collection, and doesn't need to when collection *is* authorized.** If a source's terms permit automated access, there's no need to hide results from the user -- the existing `active` sources show up immediately. If a source's terms don't permit it, delaying when the UI shows the data changes nothing about whether the collection itself was authorized; the violation already happened at fetch time. "Grows quietly in the background" was already evaluated for Built In specifically and rejected on this exact reasoning (see that file's addendum) -- the same logic is source-agnostic.

**This project already has a real precedent for "general browser/agent-based scraping": issue #8, decision DEFER.** Its resume conditions are specific and evidence-based -- source-gap telemetry naming sites with no usable API/feed/sitemap/JSON-LD, a proven representative case, and packaging cost justified by real incremental coverage -- not "add an AI agent so it can cover anything." A general always-on AI scraping agent is a broader, less-governed version of exactly what #8 already chose not to build without that evidence.

## What "continuously growing job source" should actually mean here
The project already has the lever for this, and it doesn't require an AI agent: issue #9 (source-gap telemetry) feeding the epic at #10 (expand vacancy-source coverage). Growth happens by reviewing and adding one more source at a time -- API first, feed/sitemap second, ATS JSON-LD third, browser automation only per #8's resume conditions -- each with its own documented reason in `source-registry.ts`, the same way Himalayas/Jobicy/Remotive/Freehire/etc. were added. That is a continuously growing source pool, achieved without a general-purpose scraping agent and without the legal exposure #32 already catalogued for LinkedIn/Indeed-style unauthorized-access patterns.

## Non-goals
Do not build a general-purpose AI scraping agent, "grow the corpus quietly" background crawler, or any mechanism that adds vacancy sources without the individual per-source review this project already requires. A specific site with genuinely permissive terms is still welcome -- as its own reviewed source-registry entry, checked the same way Built In just was.

## Clarification: a *discovery* agent is a different, already-scoped idea
Following discussion, the actual goal isn't an agent that scrapes and stores job listings -- it's an agent whose job is finding and evidence-gathering *candidate sources*, one at a time, the same way this session just did for Built In by hand: identify a candidate site, fetch its `robots.txt`, fetch its Terms of Use, check for a public API/feed/JSON-LD, and write up a dossier. That's a fundamentally different risk profile:

- It never collects or stores job listing data -- only public policy documents (`robots.txt`, ToS pages) that are meant to be machine-read, plus checking whether a documented API exists.
- Its output is a candidate write-up for human/ticket review, not ingested vacancies -- the same shape as `draft-builtin-source-research.md` or the existing "research"-labeled spike issues (#50, #51, #52, #53, #30, #32).
- It maps directly onto work this project already scoped: issue #9 (source-gap telemetry) and epic #10 (expand vacancy-source coverage using open-source scraper research) -- this would be an agent-assisted way to produce candidates for that epic faster, not a new category of work.
- It doesn't obviously need new runtime infrastructure (no `agent-browser`/MCP tool required) -- `robots.txt` and ToS pages are plain HTTP fetches, the same tools used in this session's research would do.

If this is the direction to pursue: scope it as a discovery/evidence-gathering task feeding issue #9 / epic #10, output one candidate dossier per source (decision left to the human, per #32's "provider-by-provider... independently satisfy OVR's source policy" rule) -- never as a component that itself decides to start ingesting a source's listings.

## The three-stage pipeline, mapped onto what exists

The fuller shape discussed: (1) a discovery agent finding candidate portals/aggregators, (2) a scraping agent that ingests a source once it's cleared, (3) an aggregation step that serves results when the user searches. Mapping each stage onto this repo's actual architecture:

1. **Discovery -- new, AI-agent-shaped.** Covered above: evidence-gathering only, feeds #9/#10, output is a reviewed dossier, never auto-approves itself.
2. **Scraping "only when allowed" -- should not itself be an AI agent at runtime.** Once a source clears review, this repo's existing pattern (`packages/vacancy-engine/src/ats/*`, `src/global-remote/*`) is a deterministic, per-source adapter: fixed parser, strict schema validation, run through `SafeHttpClient`/the crawler's caching and rate-limit machinery (`src/crawler/scheduler.ts`, `http-cache.ts`, `url-safety.ts`). `docs/mcp-source-policy.md` requires exactly this shape for every provider ("fixed argument mapper, strict output parser"). An LLM agent improvising extraction on every run would be harder to audit, cache, and rate-limit than a reviewed parser -- so an AI agent's role at this stage is *building/reviewing* the adapter once (e.g. confirming Built In's pages carry JobPosting JSON-LD, as this session did), not being invoked as a live scraper each run.
3. **Aggregating results at search time -- already built, not an agent.** `packages/vacancy-engine/src/vacancies/repository.ts` (`persistVacancyScan`) and `src/scoring/service.ts` (`scoreActiveVacancies`, using `DETERMINISTIC_SCORING_VERSION`/`scoreVacancy` from `src/filtering/*`) already aggregate every active source into one vacancies table and score/rank it deterministically against the candidate profile on search. This is deliberately deterministic, not LLM-driven -- consistent with the project's standing "no default role/country/salary bias" discipline, which depends on scoring being auditable rather than a model's judgment call. No third agent is needed here; it's the existing query/scoring pipeline every source (including a newly approved one) already flows into automatically once its adapter writes into the shared vacancies table.
