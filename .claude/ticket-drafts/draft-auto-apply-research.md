## Goal
Research the feasibility of an AI-driven "auto apply" flow: read a vacancy's job description, tailor the user's CV to it, draft a cover/motivation letter if the target expects one, then fill and submit the application form -- the flow already prototyped once in Codex using a browser tool, per the user. This ticket records what's already in place, what's missing, and the hard constraints that apply regardless of how it's built. Not scoped for implementation yet.

## What already exists in this app for this
- **Job description data**: vacancy detail already carries posting text pulled through the existing ATS adapters/`json-ld.ts` extraction (`packages/vacancy-engine/src/ats/*`) -- no new discovery work needed to get JD text for an already-ingested vacancy.
- **Letter generation is fully implemented already**, not just a supporting piece: `apps/desktop/src/components/cv/CoverLetter.tsx` + `buildCoverLetterPrompt` (`apps/desktop/src/components/cv/prompts.ts`) already draft a per-vacancy motivation letter from the loaded CV, streamed live through `useAgentRun` (the Claude/Codex CLI, never a held API key), with prompt-injection defenses around the untrusted scraped vacancy text and an explicit "this is a first draft, not a submission" disclaimer in the UI. There's a second, separate letters surface too: `apps/desktop/src/components/letters/{LetterGenerator.tsx,prompt.ts}` (four document types), which `draft-search-letters-handoff.md` (issue #136) is wiring to a "Generate Letter" action straight from a Search-page vacancy. Either way, letter generation for a specific JD is a solved, already-reviewed step, not new work.
- **CV data and comparison, partially implemented -- but not tailoring.** `apps/desktop/src/components/cv/GapAnalysis.tsx` + `buildGapAnalysisPrompt` already compares a loaded CV against one vacancy and returns an advisory report (Strengths / Gaps / How to close gaps / Overall fit) -- but it's analysis text for the user to act on themselves, not a rewritten CV. `buildCvParsePrompt` extracts structured fields from a CV (for CV Library storage / the profile bridge in `draft-cv-profile-bridge.md`), which also isn't tailoring. Nothing today takes a CV and a specific JD and produces an adapted CV document.
- **The review-before-save convention**: every AI-extraction feature in this app so far (CV parsing, the proposed CV-profile bridge) shows the model's output to the user before anything is written or sent. Auto-apply would need the same discipline at its most consequential step (see Non-negotiables below), not a lighter version of it.

## What's genuinely missing
1. **CV tailoring to a specific vacancy.** The closest existing feature, `GapAnalysis.tsx`, only reports what matches and what's missing -- it doesn't rewrite or adapt the CV's content itself. Producing an actual tailored CV document is new AI work, distinct from gap analysis and from the CV Library's parse-to-structured-fields flow.
2. **Form fill + file upload + submit automation.** This needs real browser-driving capability. Per `draft-agent-browser-mcp-tool.md`, that capability (`agent-browser`) is deliberately not being built in this repo -- the AgentDock dev AI's direction was that it belongs upstream in `jortega0033/agentdock`, pulled in here afterward. Auto-apply's fill/upload/submit stage is directly blocked on that pull happening, and even then, only the read-only slice was scoped there -- interactive tools (`click`/`fill`/`type`) were explicitly deferred pending "a dedicated ticket designs a confirm-before-submit gate," which is essentially this ticket's job once it's picked up.
3. **Per-platform legal review**, the same discipline `docs/mcp-source-policy.md` and issue #32 already apply to scraping, but for *applying* rather than collecting data. Not every job form carries the same risk:
   - Platforms with an explicit blanket bot/automation prohibition are a hard no the same way scraping them is. Issue #32's own evidence already found this for LinkedIn ("LinkedIn expressly prohibits scraping, bots, copying through third-party aggregators, access-control circumvention, and unauthorized deep links") -- that prohibition covers automated Easy Apply the same as it covers scraping.
   - A company's own careers/ATS application form (Greenhouse, Lever, Workday, etc.) is a different risk shape: usually no blanket "no bots" clause the way LinkedIn has, but submitting via an AI-driven agent still raises questions this ticket doesn't resolve -- e.g. whether an undisclosed AI-authored application misrepresents the applicant, and whether high-volume auto-submission across many postings reads as spam to the employer/ATS's own abuse detection. This is a quality/ethics question as much as a legal one, and is per-platform, not blanket-answerable here.
4. **No credential entry, still.** Any application form requiring the user to log in (an ATS account, a platform login) is out of scope for automation -- the standing prohibition on entering the user's credentials (see `draft-agent-browser-mcp-tool.md`'s non-goals) applies here without exception. Only guest/no-login application forms, or forms within a session the user is already authenticated in themselves, are even candidates.

## Non-negotiables, not just design preferences
- **A human must explicitly confirm before final submit, every single application, forever** -- this isn't a workspace-level trust toggle that, once granted, lets the agent submit unattended. Submitting a job application is an irreversible, consequential real-world action with the user's real name and data attached; per-action confirmation is required regardless of how much of the pipeline (JD read, CV tailor, letter draft, form fill) runs unattended before that point.
- **No auto-submit mode should ever exist**, even behind a setting. The tailoring/drafting/filling stages can run ahead of the user and wait for review; the submit click cannot be pre-authorized in bulk.
- **The user sees exactly what will be submitted** -- tailored CV, letter, and every filled form field -- before confirming, the same way CV-parse review works today, not a summary or a "trust me" confirmation.

## What would need to be true before this is worth building
1. `agent-browser` (or equivalent) has actually landed via the AgentDock upstream pull (`draft-agent-browser-mcp-tool.md`), with its read-only slice proven first.
2. A CV-tailoring prompt/flow exists and has been reviewed the same way `buildCvParsePrompt` was.
3. A confirm-before-submit UI has been designed and is understood to be mandatory, not configurable away.
4. At least the LinkedIn-style "hard no" platforms are identified and explicitly excluded before any pilot, the same way this project already excludes LinkedIn/Indeed from scraping (issue #32's "Hard exclusions").

## Non-goals
Not building any part of this now. Not deciding per-platform legality here -- that's individual research per target site when this is picked up, the same as source discovery. Not designing the confirm-before-submit UI in this ticket -- flagging that it's mandatory, not optional, is as far as this research goes.

## Risk
High if ever built without every non-negotiable above enforced at the code level (not just prompt instructions) -- this is the single most consequential automation this app could ship, submitting real applications under the user's real identity to real employers.
