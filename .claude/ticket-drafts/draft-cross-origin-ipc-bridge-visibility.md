## Goal
Let the review UI and the field-map generation session see which frame each field actually lives in, so a person reviewing an application (or the AI assigning values to fields) can reason about a cross-origin field the same way `packages/application-executor` now can.

## Why now
The September 2026 architecture audit's F-D finding (cross-origin iframe field-fill has no origin check) was fixed and merged this session: `dom-extract.ts`/`executor.ts` now refuse to fill any field whose frame origin differs from the top document's unless a policy explicitly allowlists it (`isFrameFillAllowed`, `target-policy.ts`). That fix closes the write path. But the fix's own implementer flagged a real, adjacent gap in their final report: `apps/desktop/electron/preload.ts` (~line 1230) rebuilds a sanitized snapshot field-by-field for the renderer, and that rebuild does not carry `frameOrigin`/`topFrameOrigin` across the IPC bridge. So while a cross-origin field can no longer be *filled*, nobody on the desktop side of the bridge -- not the review UI a person looks at, not the field-map generation session an AI call drives -- can currently see or reason about which frame a field came from at all. A field silently refused for being cross-origin shows up to a reviewer as an unexplained blocker, not as "this field lives in a third-party widget, not the real form."

## Scope
- Extend whatever sanitized snapshot shape `preload.ts` sends to the renderer to include each field's `frameOrigin`, and the snapshot's own `topFrameOrigin`, mirroring what `FormSnapshot`/`SnapshotField` already carry inside the executor package.
- Surface it somewhere a person reviewing the application can actually see -- at minimum, a distinct, person-readable explanation for a field the executor found but never fills because it lives in a different frame's origin, so a reviewer can tell "this app never had the option of filling this" apart from an ordinary readiness problem.
- Consider whether the field-map generation session's own prompt should be told a field's frame origin, so the AI assigning values can avoid proposing an assignment to a field it already knows will be refused, rather than proposing it and having the executor silently drop it.

**Correction after reading the real code (this session):** the scope above originally said this should be "a blocker ... distinct from 'required field empty' or other existing blocker kinds," describing it as a new `ReadinessBlocker` kind in `form-readiness.ts`. That is not what the actual data shows, and not what this implementation does:

- `evaluateFormReadiness` (`form-readiness.ts`) only ever considers `field.active` fields when building `blockers` (`snapshot.fields.filter((field) => field.active && !field.classification)`). A disallowed cross-origin field is therefore invisible to readiness on *some* pages but not all, and the difference is what the first implementation of this ticket got wrong. On a page that has a same-origin form of its own, `resolveActiveGroup` drops the vendor's group and `activeFrameId` stays on the employer's own frame (`cross-origin-frame-fill.test.ts`'s "refuses the vendor embed by default"), so the vendor's fields are `active: false` and produce no blocker at all. But when the policy authorizes *no* group on the page -- the page the ticket was actually written about, whose entire form lives in one disallowed embed -- `resolveActiveGroup` returns the count-based fallback (`executor.ts`: `if (eligible.length === 0) return fallback;`) and `readPageState` marks those very fields `active: true`. They then produce ordinary `required_field_empty` blockers with no explanation, while `fill()` still refuses them at `requireFillableFrame`. So "a cross-origin-excluded field is never active" is false, and keying any visibility on `!field.active` goes blind on the one page shape that needs it most. Both surfaces added by this ticket key on `frameOrigin !== topFrameOrigin` instead -- the same comparison `isFrameFillAllowed` makes -- and use `active` only to pick the wording: `active: true` means the form under review is itself inside the embed, `active: false` means the field is elsewhere on the page and not part of the form under review. The gap this ticket closes is both halves: fields that never reach readiness at all, and fields that reach it as unexplained blockers.
- Adding a genuinely new `ReadinessBlocker` kind would mean editing `packages/application-executor/src/form-readiness.ts` (and its `describeBlockers`), which is out of scope for this pass (the implementer was asked to touch only `apps/desktop`, reading but not modifying the executor package that already carries the needed `frameOrigin`/`topFrameOrigin` types from this morning's fix).
- Implemented instead: an additive, apps/desktop-only notice computed from `snapshot.fields`/`snapshot.topFrameOrigin` (already carried across the bridge once preload.ts is extended per the first scope bullet), surfaced in `ApplicationReviewSwipeCard.tsx` alongside but structurally separate from `readiness.blockers` -- it never changes `readiness.ready`, `blockers.length`, or any other package-owned reading. This satisfies the actual intent ("a person reviewing can reason about a cross-origin field") without redesigning `form-readiness.ts`'s closed blocker union. A future pass that wants this to be a first-class `ReadinessBlocker` kind (so it also appears in `describeBlockers`' plain-text summary, e.g. for a notification body) would need to touch the executor package and is left as a follow-up.

## Non-goals
- No change to the refusal logic itself (`isFrameFillAllowed`, `resolveActiveGroup`) -- that's already correct and tested; this ticket is purely about making the existing decision visible on the other side of the IPC boundary.
- No new policy-configuration UI for `allowedSubFrameOrigins` -- that stays a code-reviewed policy field, per `target-policy.ts`'s existing "never JSON/config" discipline.

## Acceptance criteria
- A fixture page with a cross-origin embedded widget (reusing `packages/application-executor/test/cross-origin-frame-fill.test.ts`'s fixture shape) shows a person-readable, frame-origin-specific notice in the review UI, distinct from every ordinary readiness-blocker message and clearly not part of `readiness.blockers` itself.
- The field-map generation session's prompt-building code has access to per-field frame origin, verified by a new test asserting it's present in the bundle passed to the session -- including the zero-eligible-group page (the whole form inside one disallowed embed, so every field comes back `active: true` with the vendor's origin), which is the case the `!active` qualifier missed. This criterion originally read "a new test confirming an *active* cross-origin field is never flagged, since that one really is fillable", on the assumption that an active cross-origin field only ever means a policy-allowlisted vendor embed. It does not: the fallback path above produces active cross-origin fields that are refused at the write. Since a policy's `allowedSubFrameOrigins` is not carried to either surface (and no shipped policy names one today), both describe an active cross-origin field as unfillable; the first policy that allowlists a sub-origin must pass its allowed origins into `describeField`/`crossOriginFields` rather than let them keep inferring from origins alone.
- No change to any existing test's assertions about same-origin pages -- this is additive visibility only.

## Risk
Low. This is a read-only visibility extension across an existing IPC boundary and prompt-input bundle -- no new write path, no new trust decision. The only real risk is scope creep into redesigning the blocker/UI copy system; keep this to "surface the data that already exists one level deeper," not a UI redesign.
