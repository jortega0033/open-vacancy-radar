## Goal
Add an origin check to the application-executor's "active frame" field-fill path so it never types real form data into a cross-origin iframe without either confirming that frame's origin matches the top document (or an explicit allowlist on the target policy), closing the gap identified in the Sept 2026 architecture audit's security review.

## Why now
DOM extraction pierces every iframe on a page including cross-origin ones (`packages/application-executor/src/dom-extract.ts:242-245`, `pierce:true`). The "active" frame/form selection that decides which frame's fields get filled -- `mostCommon` in `dom-extract.ts:207-224` and `resolveActiveGroup` in `executor.ts:219-270` -- picks by field count and geometry only, with no check that the winning frame's origin matches the target policy's authorized origin or the top document's origin. The one origin check that exists in this path, `isNavigationAllowed` (`target-policy.ts:80-91`), only gates top-level navigation; it says nothing about which iframe receives filled values. `executor.ts:232-239`'s own docstring frames the risk as same-origin only -- "a page steering which of its own controls receives an answer" -- but that framing does not hold for a cross-origin embedded widget (chat, cookie-consent, job-alert signup): those are not "the page's own controls," they are a third party's. `Input.insertText`/`dispatchMouseEvent`/`dispatchKeyEvent` are on the allowed CDP list (`cdp-allowlist.ts:42-44`) and fire real DOM input events that many third-party widgets read live, so a wrong-frame fill is not inert -- it can hand real field values to code the target site does not control. The risk is sharpened by `application-pipeline.ts:654-698`, which calls `openApplicationReview`/`applyApplicationFieldMap` directly from the unattended background tick with no human in the loop, and by `application-review-session.ts:1111`, which fires automatic submission later -- so on a `termsEligibleForAutomation` policy, PII could reach a third-party widget with nobody watching. Mitigating factor: automatic mode requires an explicit `termsEligibleForAutomation` policy (`target-policy.ts:54-66`), and today `application-target-policies.ts` has exactly one entry and it is fixture-only, so this is not yet reachable for a real user. That is exactly why it belongs on the board now, before any real policy ships and turns a theoretical gap into a live one.

## Scope
- Add an origin check to `resolveActiveGroup`/`extractSnapshotFields` (`packages/application-executor/src/executor.ts:219-270`, `dom-extract.ts:207-224,242-245`): scope "active" frame/form resolution to same-origin frames by default, so a cross-origin frame cannot win the field-count/geometry contest silently.
- Where a field-mapping caller does need to reach into a cross-origin frame (a legitimate embedded application widget), require it to see and reason about that field's frame origin before assignment, rather than resolving and filling blind.
- Refuse fill on any field whose frame origin differs from the top document's origin unless the target policy explicitly allowlists that sub-origin.
- Extend `target-policy.ts` (near the existing `isNavigationAllowed`, `target-policy.ts:80-91`) with the allowlist concept and policy field needed to express "this specific cross-origin sub-frame is authorized," so legitimate embedded-widget cases keep working without an origin check that is all-or-nothing.

## Non-goals
- Not building a general cross-origin sandboxing framework for the executor -- scoped to the field-fill/active-group-resolution path named above.
- Not touching `isNavigationAllowed` or top-level navigation gating (`target-policy.ts:80-91`) -- that check already works for its own purpose and is out of scope here.
- Not writing or shipping any real `termsEligibleForAutomation` policy -- `application-target-policies.ts` stays fixture-only as part of this ticket; that's separate work.
- Not changing DOM extraction's `pierce:true` behavior itself (`dom-extract.ts:242-245`) -- extraction can keep seeing into cross-origin frames; the fix is at the fill/write decision, not the read.

## Acceptance criteria
- `resolveActiveGroup` (or its caller) rejects filling a field whose frame origin differs from the top document's origin, unless that origin is explicitly allowlisted on the active target policy.
- A test simulating a page with a same-origin form plus a higher-field-count or larger-geometry cross-origin iframe (e.g. an embedded chat or cookie-consent widget) confirms the same-origin form is chosen, not the cross-origin one, even though today's field-count/geometry heuristic alone would pick the cross-origin frame.
- A test confirms that a policy carrying an explicit sub-origin allowlist entry permits fill into that specific cross-origin frame, and no other.
- No change in behavior for the common same-origin-only case: existing `resolveActiveGroup`/`extractSnapshotFields` tests for single-origin pages continue to pass unmodified.

## Risk
Medium. No real user is exposed today because zero real `termsEligibleForAutomation` policies exist (`application-target-policies.ts` is fixture-only), so this is a hardening fix ahead of exposure rather than an active incident. The risk is in getting the origin-allowlist plumbing right: too strict and legitimate embedded-widget application flows silently stop working (falling into a refusal state) instead of erroring loudly; too permissive and the fix is cosmetic. The fixture-only status of real policies also means there's no production case to validate against yet -- test coverage has to be built from constructed same-origin/cross-origin scenarios rather than an observed real-world one.
