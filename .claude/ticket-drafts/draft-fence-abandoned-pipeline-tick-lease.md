## Goal
Make a hard-timed-out application-pipeline tick actually free the daemon's global lease, instead of only freeing the *ticker's* in-flight guard the way today's fix does -- without letting the abandoned, still-running `runApplicationAttempt` call corrupt state once it eventually does settle.

## Why now
This is the harder half of F-A from the September 2026 architecture audit (`.claude/audits/full-system-audit-2026-09-15.md`, §5/§18/§19), and the one piece of the audit's "First Implementation Batch" not yet implemented. What's already shipped this session:
- `withHardTimeout` (now inside `createTick`, `apps/desktop/electron/tick.ts`) bounds one *tick's* wait, so the recurring worker itself keeps polling after a hang instead of being permanently wedged (`applicationPipelineTick.inFlight` correctly resets to `false` once the hard timeout elapses -- see `test/tick.test.ts`'s hang-simulation case).
- The daemon now clears a lease left over from a *previous process life* on startup (`ApplicationQueueStore#reconcileStaleLeaseOnStartup`, `apps/daemon/src/application-queue-store.ts`) -- this closes the "survives an app restart" half of the bug.

What's still open: **within one continuous Electron process/daemon lifetime**, a tick that hits its hard timeout does not release the lease at all -- the abandoned `runApplicationAttempt(deps, attemptId)` call keeps running in the background and still holds it. `acquireNextLease()` then returns `null` forever until the user manually restarts the whole app, exactly the original incident, just narrowed to "still up" instead of "across a restart."

The adversarial reliability review (folded into the audit) found the obvious fix -- have the hard-timeout path call `queue.release(lease.leaseId, 'requeue')` directly -- is **unsafe as stated**: `release()` immediately returns the queue entry to `'queued'`, the next 15s tick re-acquires a fresh lease for the *same* attempt id, and the original abandoned promise is still running. Two concurrent `runApplicationAttempt` calls for one attempt can then both write `applicationAttempts` checkpoint/`preparedFields` columns (interleaved, last-write-wins, checkpoint can flap backward) and both stage PDF artifacts under the same `storageRoot/<attemptId>/` directory. It does **not** reopen the double-real-submission hazard -- `submittingAttemptIds` (`application-review-session.ts:536-547`) independently fences the actual `executor.submit()` call regardless of how many stale preparation runs are in flight -- but it does reopen data-corruption/resource-leak hazards the single-lease model was also implicitly relying on to avoid.

## Scope
- A fencing/generation mechanism scoped to *preparation*, mirroring `submittingAttemptIds`'s shape but for this different problem: before `runNextApplicationAttempt` starts working on an attempt, record a generation marker (an in-process `Map<attemptId, generation>` is enough -- this does not need to survive a restart, since a restart already goes through `reconcileStaleLeaseOnStartup`). Increment/replace the marker whenever a *new* lease is acquired for that attempt id.
- On the hard-timeout path in `applicationPipelineTick`'s `run`, force-release the lease (`queue.release(lease.leaseId, 'requeue')`) **and** bump/discard the generation marker for that attempt id so the next lease acquisition gets a fresh generation.
- Every DB write `runApplicationAttempt` makes (checkpoint updates, `preparedFields`, artifact staging) must check its own captured generation against the current one before writing, and silently skip (not throw -- the run genuinely was abandoned, this is not an error) if it no longer matches. This likely means threading the generation value through `ApplicationPipelineDeps` or wrapping the DB calls `runApplicationAttempt` makes, not touching every call site individually -- look for the narrowest chokepoint (e.g. wrapping `workspace.updateApplicationAttempt`/`recordFetchedJobDescription`/the artifact-staging write for one attempt) before spreading a generation check across the whole 858-line pipeline file.
- Orphaned PDF artifacts from an abandoned run's late, discarded write should still get cleaned up -- this can likely reuse or extend the existing orphaned-artifact cleanup already flagged as P2 in the audit (`restartApplicationTailoring` leaking files on disk), rather than being a separate mechanism.

## Non-goals
- No change to the daemon's own lease/queue model beyond calling the existing `release()` with `'requeue'` at the right moment -- this is a fencing problem on the Electron side, not a redesign of `ApplicationQueueStore`.
- No change to submission-time safety (`submittingAttemptIds`) -- already independently correct per the adversarial review, not touched by this ticket.
- No general-purpose "cancel a promise" mechanism (`AbortController` threaded through every AI/CDP call) -- that's a larger, separate hardening effort (the audit's `challenge:application-prep` finding on unbounded CDP/PDF calls) and not required to close this specific gap: fencing makes an abandoned run's *effects* harmless without needing to actually stop the run itself.

## Acceptance criteria
- A simulated hang (a `run` that never resolves, exercised the same way `tick.test.ts` already does) that hits `APPLICATION_PIPELINE_TICK_HARD_TIMEOUT_MS` results in: the lease is released and re-acquirable by the next tick, and a late write from the original abandoned call (simulated by resolving it after the fence has moved on) is verifiably discarded rather than applied.
- A normal, non-hung run is completely unaffected -- same checkpoint/artifact behavior as today, no user-visible change to the golden path.
- New tests cover: the fenced-discard case above; that a *legitimate* slow-but-not-stuck run occurring entirely within one generation still writes normally; and that two full lease cycles for the same attempt id (hang, force-release, re-acquire, genuine completion) end with the attempt in a coherent final state, not a mix of the abandoned and the fresh run's writes.

## Risk
High. This is a concurrency-correctness primitive protecting real user data (which CV/cover-letter text ends up attached to a real application) against a genuinely rare but real failure mode (a stuck CDP call or an untimed AI session). Get the fencing scope wrong -- too narrow, and a late write still lands; too broad, and a legitimately slow but real run gets silently discarded -- and this ticket makes things worse, not better. Land it behind the same kind of hang-simulation regression test `tick.test.ts` already established as the standard for this code class, and have a second pass (independent review, not just the implementer) specifically try to find a write path the fence misses before considering this closed.
