## Goal
Show a first-launch "Welcome" modal that invites a new user to upload their CV, optional and skippable, so the app's actual on-ramp (CV Library -> "Fill from CV" -> a configured search profile) isn't something a brand-new user has to discover on their own.

## Why now
Nearly every feature in this app assumes a CV is already in the library: `SearchProfileSection`'s own "unconfigured" warning (`profile.targetRoles.length === 0 && profile.strongestSkills.length === 0`) fires the moment a fresh user opens Settings, and the just-widened "Fill from CV" (issue #137's follow-up, this session) has nothing to read from without one. Today a brand-new user lands on the Search tab with an empty, unscored profile and no prompt anywhere pointing them at CV Library -- they either find it by exploring the sidebar or never do. The existing "unconfigured" banner is reactive and buried inside Settings > Search; nothing nudges them proactively at the one moment (first launch) it would matter most.

## Scope
- A new `WelcomeModal` component (`apps/desktop/src/components/WelcomeModal.tsx`), shown from `App.tsx` on first launch only, before any page-specific content, matching the existing DaisyUI modal convention (`FillProfileFromCvDrawer`'s `modal modal-open` structure: header with a close button, body, footer with a secondary "Skip for now" and a primary "Upload CV" action).
- Reuses the CV Library's own upload composition as-is: `CvUploadAction`'s `window.cv.selectAndRead()` -> `SaveCvToLibrary`'s `window.workspace.createCvDocument(...)` path. No new IPC channel, no new main-process code, no changes to CV extraction/parsing.
- A new persisted `welcomeSeen` boolean on `app_settings` (workspace.db), following the exact 6-file pattern `defaultProvider` already establishes: `electron/workspace/schema.ts`, a generated `electron/workspace/drizzle/00XX_*.sql` migration, `electron/workspace/types.ts` (`AppSettingsRecord`), `electron/workspace/repository.ts` (`toSettings()`), `electron/workspace/validate.ts` (`parseSettingsPatch`). No IPC channel changes needed: `workspace:settings:get`/`workspace:settings:update` already round-trip the whole record.
- Gating logic, decided to avoid re-showing this to existing users on upgrade without hand-editing the generated migration's default: the modal renders only when **both** `!settings.welcomeSeen` **and** the CV library has zero documents at mount (`listCvDocuments()`). An existing user who already has a CV on upgrade never sees it flash -- `welcomeSeen` is set to `true` immediately, silently, the first time that combination is checked and a CV already exists. A user with no CV yet (new or existing) sees it once; skipping or uploading both mark `welcomeSeen: true` so it never reappears.

## Non-goals
- No multi-step wizard beyond upload -> auto-started profile review; no forced/blocking modal -- it must be dismissible at every step without uploading anything or saving a profile (this is "highly recommended," not required; forcing it would gate the app behind an action the user may not want yet).
- No re-showing logic, reminder banners, or "you skipped this" follow-ups later -- `SearchProfileSection`'s existing "unconfigured" banner already covers the ongoing nudge once the user is past first launch.
- No changes to CV upload/extraction/`createCvDocument` validation, and no new AI-extraction logic -- this reuses "Fill from CV" (`FillProfileFromCvDrawer`, widened earlier this session) exactly as it already exists in Settings, via one new `autoStart` prop, rather than building a second extraction flow.
- Does not touch `candidate-profile-v1.json` or any shipped default -- consistent with this project's no-default-bias precedent, since nothing here writes a role, country, or salary value without the user reviewing and pressing Save first.

## Revision: the upload alone was not the point
The first pass of this ticket stopped at saving the CV to the library and closing the modal. That missed the actual purpose: a document sitting unused in the library does nothing for scoring or for the fields `SearchProfileSection`'s own "unconfigured" banner is unhappy about -- the search profile has to actually get filled in. So a successful upload now hands off into `FillProfileFromCvDrawer` with a new `autoStart` prop (reads the just-uploaded, now-default CV itself, no "Read CV" click needed) instead of closing immediately. The review-before-save contract is unchanged: the user still sees the nine extracted fields and presses Save (or Cancel) themselves; `onClose` fires the same way whether they save, cancel, or the whole thing is skipped at the very first step -- the CV is already in the library by the time the profile-review step is reachable at all, so there is no path that loses the upload.

## Acceptance criteria
- A user with an empty CV library and `welcomeSeen: false` sees the Welcome modal on launch; "Skip for now" closes it and persists `welcomeSeen: true` without uploading anything.
- "Upload CV" runs the exact same pick-and-save flow CV Library's own upload button uses; on success it hands off into `FillProfileFromCvDrawer` (autoStart, no manual "Read CV" click) for the just-uploaded CV, not straight to closing.
- Saving that review closes the whole welcome flow and persists `welcomeSeen: true`; cancelling out of it (after stopping an in-flight run, same as the drawer already requires) also closes the whole flow and persists the flag, since the CV itself was already saved regardless of what happens to the profile.
- A user who already has at least one CV in their library never sees the modal, on first launch or any later one, and `welcomeSeen` is silently marked `true` for them the first time it's checked.
- Once `welcomeSeen` is `true`, the modal never renders again, regardless of CV-library state.
- New DB column ships via a real Drizzle migration (`workspace:db:generate`), not a hand-written one, and existing `app_settings` rows are unaffected beyond gaining the new column at its schema-level default.
- Existing `App.tsx`, `SearchProfileSection`, CV Library, `FillProfileFromCv`, and workspace-settings tests are unaffected; new tests cover: modal shown for an empty library + unseen flag, modal suppressed for a non-empty library (and the flag gets set), skip persists the flag without uploading, a successful upload auto-starts the profile review with no manual click, saving that review closes the whole flow and persists the flag, cancelling it also closes the whole flow and persists the flag, `autoStart` never fires a second run if the user changes the selected CV afterward, and `autoStart` does nothing when the library is empty.

## Risk
Low. Additive DB column plus one new renderer component; no existing IPC surface, validation allow-list shape, or CV extraction/parsing path changes -- the only touched allow-lists (`parseSettingsPatch`, `toSettings()`) gain one more line each, mirroring `defaultProvider`/`minimizeToTrayOnClose` exactly.
