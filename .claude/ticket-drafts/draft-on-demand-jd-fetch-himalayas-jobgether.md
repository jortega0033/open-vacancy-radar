## Goal
Let "Prepare application" succeed for real Himalayas and Jobgether vacancies that have no `description` captured during the scan, by fetching the individual job page on demand at application-prepare time, the same way `fetchAiDevJobDetail`/`fetchRemooteJobDetail` already establish for other sources (currently unwired standalone helpers, per `packages/vacancy-engine/src/global-remote/ai-dev-jobs-discovery.ts:247-250`).

## Why now
Live-tested against the real app this session: a real scan (Frontend Engineer, Netherlands) returned 3 real, live vacancies across Himalayas and Jobgether. All 3 failed "Prepare application" with "no job description was captured for this vacancy" (`apps/desktop/electron/application-pipeline.ts:390-400`, a pure local read of `vacancy.description ?? ''` set once at scan time). Root-caused: `discoverHimalayas` (`packages/vacancy-engine/src/global-remote/discovery.ts:93-108`) and `discoverJobgether` (`packages/vacancy-engine/src/global-remote/structured-discovery.ts:415-430`) build their vacancy records from list/search endpoints only and never include a `description` field -- unlike sources whose list API already returns one inline (e.g. `discoverJobicy`), and unlike `discoverAiDevJobs`/whatever calls `fetchRemooteJobDetail`, neither has any per-job detail fetch at all, wired or not. Independently verified the Jobgether offer page (`https://jobgether.com/offer/<id>-<slug>`) is a real, fully readable page with a substantial job description -- not bot-blocked -- so this is a genuine coverage gap, not a source that is unscrapable by design.

## Scope
- A `fetchJobgetherJobDetail(url)` helper in `structured-discovery.ts` (or a sibling module, matching `fetchAiDevJobDetail`'s placement convention): fetches the individual Jobgether offer page and extracts the real job-description text, isolated from page chrome (nav, "Related jobs", "Other jobs at X", premium upsell copy, footer link farm -- all confirmed present on the real page and must not leak into the extracted description). Check first whether Jobgether exposes a per-job JSON endpoint (the list endpoint is `astroapi/ai/jobs.json`; a per-id sibling may exist and would be far more reliable than HTML scraping) before falling back to HTML parsing.
- A `fetchHimalayasJobDetail(url)` helper, same shape. Himalayas' individual job pages are Cloudflare-protected (confirmed directly this session: `himalayas.app` served "Just a moment... Performing security verification" to a real fetch attempt). This helper must fail cleanly (return `null`/no description) when it hits that challenge, exactly like today's silent-`null` convention (`discovery-shared.ts:118/157`) -- **no bot-detection bypass of any kind**, per this project's hard constraint. Prioritize the Jobgether half of this ticket; the Himalayas half may simply document "still blocked, by design" as an acceptable outcome rather than a fix.
- Wire both into `application-pipeline.ts`: when `startApplicationAttempt` finds `vacancy.description` empty and the vacancy's source is Himalayas or Jobgether, attempt the on-demand fetch before falling back to today's `needs_user` refusal, and persist the fetched description onto the vacancy record (or the attempt's own snapshot -- match whichever the existing schema/flow expects) so a second attempt doesn't refetch every time.
- Real, bounded network timeout and a single retry at most -- this runs synchronously in the user-facing "Prepare application" click path, not a background scan.

## Non-goals
- No change to the bulk scan's own list-scraping behavior (`discoverHimalayas`/`discoverJobgether` stay list-only; this is an on-demand, single-vacancy fetch triggered only when a user actually tries to prepare an application for that specific listing, not a change to what happens for the other ~20,000 rows a scan touches).
- No CAPTCHA/bot-detection bypass for Himalayas, ever -- a hard constraint, not a scope trade-off.
- No change to how any other source (Jobicy, RemoteOK, etc.) populates description.

## Acceptance criteria
- A real Jobgether vacancy with no captured description succeeds at "Prepare application" via a live on-demand fetch, with the description text free of nav/related-jobs/footer chrome.
- A real Himalayas vacancy behind Cloudflare still shows the existing "no job description was captured" message (or an equally honest "could not fetch: source blocked automated access" message) -- never a fabricated or bypassed description.
- The fetch has a real timeout and does not hang "Prepare application" indefinitely if the source is slow or unreachable.
- New tests cover: successful Jobgether detail fetch and chrome-stripping, a Jobgether fetch that 404s/changes shape failing cleanly, and a Himalayas fetch hitting a bot-check failing cleanly with no retry-as-bypass behavior.

## Risk
Medium. This is a real, user-facing path (an actual job application can be prepared from its output) touching a currently-honest "we don't have this" refusal -- getting the chrome-stripping wrong could feed noise into a real cover letter/tailoring prompt without the failure being as obvious as today's explicit refusal. Keep the extraction conservative: prefer under-extracting (or failing) over silently including page furniture as if it were the job description.
